# Доступность

Доступность — это не функция, которую прикручивают в конце. Это свойство того, как компонент устроен с самого начала. Компоненты Altrone изначально доступны: правильная семантика, поддержка клавиатуры, управление фокусом и контраст, соответствующий WCAG AA. Эта статья объясняет правила, по которым живут эти компоненты — чтобы, когда вы будете строить собственные компоненты над Altrone (карточку, составной виджет фильтров, специфичный для вашего домена элемент формы), вы следовали тем же правилам, а не изобретали их заново.

Главный принцип прост: **сначала нативная HTML-семантика, ARIA — только там, где нативного эквивалента нет.** У `<button>` уже есть фокус, активация с клавиатуры и роль — бесплатно. `aria-role="button"` на `<div>` не даёт вам ничего из этого — всё придётся реализовывать руками, и легко ошибиться в деталях.

## Навигация с клавиатуры

Любой интерактивный элемент должен быть управляем только клавиатурой. Для одиночного контрола (кнопка, поле ввода) это работает само собой благодаря нативному элементу. Для **составного виджета** — набора связанных контролов, которые ведут себя как один узел: тулбар, список табов, кастомное меню — нужен roving `tabindex`.

Идея: только один элемент группы входит в Tab-последовательность (`tabindex="0"`), остальные — `tabindex="-1"`. Стрелки перемещают фокус *внутри* группы; Tab выводит фокус *из* неё.

```tsx filename="CustomToolbar.tsx"
function CustomToolbar({ actions }: { actions: Action[] }) {
  const [activeIndex, setActiveIndex] = useState(0);

  const handleKeyDown = (event: React.KeyboardEvent) => {
    if (event.key === 'ArrowRight') {
      setActiveIndex((i) => (i + 1) % actions.length);
    } else if (event.key === 'ArrowLeft') {
      setActiveIndex((i) => (i - 1 + actions.length) % actions.length);
    } else if (event.key === 'Home') {
      setActiveIndex(0);
    } else if (event.key === 'End') {
      setActiveIndex(actions.length - 1);
    }
  };

  return (
    <div role="toolbar" onKeyDown={handleKeyDown}>
      {actions.map((action, index) => (
        <button key={action.id} tabIndex={index === activeIndex ? 0 : -1}>
          {action.label}
        </button>
      ))}
    </div>
  );
}
```

Несколько соглашений, которые стоит соблюдать, чтобы поведение совпадало с остальной Altrone:

- **Стрелки** перемещают фокус внутри составного виджета.
- **Home / End** переносят фокус на первый / последний элемент.
- **Escape** закрывает любой оверлей (меню, поповер, дропдаун) и возвращает фокус туда, откуда он был открыт — никогда не оставляйте фокус «подвешенным» на элементе, который только что исчез.

:::tip
Если вы просто компонуете существующие компоненты Altrone (например, ряд `Button`), скорее всего roving `tabindex` строить самостоятельно не нужно — это требуется только когда вы создаёте по-настоящему новый составной виджет из сырых элементов.
:::

## Фокус: видимый, изолированный там, где нужно, возвращённый при закрытии

Три отдельных аспекта, и все одинаково важны:

**Видимость фокуса.** Стилизуйте фокус через `:focus-visible`, а не `:focus`. `:focus` срабатывает и на клик мышью, создавая рамку фокуса, которую никто не просил; `:focus-visible` показывает её только тогда, когда браузер считает, что идёт навигация с клавиатуры или вспомогательной технологии.

```scss
/* Неправильно — рамка появляется и при клике мышью */
.customControl:focus {
  outline: 2px solid var(--accent-9);
}

/* Правильно */
.customControl:focus-visible {
  outline: 2px solid var(--accent-9);
}
```

**Изоляция фокуса.** Любой оверлей, перекрывающий экран — модалка, диалог, drawer — должен удерживать фокус внутри себя, пока открыт: Tab должен циклически обходить контролы внутри оверлея и не уходить на страницу за ним. `Modal`, `Dialog` и `Drawer` в Altrone уже это делают; если вы строите собственный полноэкранный оверлей, нужна такая же изоляция (библиотека вроде `focus-trap-react` или встроенное модальное поведение нативного элемента `<dialog>` — оба разумных способа получить её, не реализуя вручную).

**Возврат фокуса.** Когда оверлей закрывается, фокус должен вернуться туда, откуда он был открыт — на кнопку, открывшую диалог, на строку, открывшую меню. Потеря этого — одна из самых частых регрессий доступности: пользователь нажимает Escape, диалог исчезает, а фокус тихо сбрасывается на `<body>`, ломая его представление о том, где он находится на странице.

```tsx filename="useFocusReturn.ts"
function useFocusReturn(isOpen: boolean) {
  const triggerRef = useRef<HTMLElement | null>(null);

  useEffect(() => {
    if (isOpen) {
      triggerRef.current = document.activeElement as HTMLElement;
    } else {
      triggerRef.current?.focus();
    }
  }, [isOpen]);
}
```

## Контролам только с иконкой нужно имя

У контрола, состоящего только из иконки без видимого текста, нет доступного имени, если вы не зададите его явно. Пользователи скринридеров ничего не услышат — или, что хуже, услышат имя файла SVG-иконки. Это **обязательное** требование, а не опция, для любого контрола только с иконкой, который вы создаёте.

`Button` в самой Altrone уже закладывает это в форму компонента: `label` — обязательный проп, даже когда `showLabel={false}` скрывает его визуально — он всё равно становится доступным именем и текстом подсказки.

```tsx
import { Button } from 'altrone-ui';
import { Settings } from 'lucide-react';

<Button label="Открыть настройки" showLabel={false} icon={<Settings />} />;
```

Если вы собираете контрол с иконкой с нуля, а не через `Button`, сделайте то же самое руками:

```tsx
/* Неправильно — у кнопки нет доступного имени */
<button onClick={onDelete}>
  <TrashIcon />
</button>

/* Правильно */
<button onClick={onDelete} aria-label="Удалить элемент">
  <TrashIcon />
</button>
```

:::warning
`title` не заменяет `aria-label` — поддержка скринридерами непостоянна, а на сенсорных устройствах он практически никогда не доступен.
:::

## Объявление изменений: `aria-live`

Некоторые изменения интерфейса происходят без перехода фокуса на какой-либо элемент — появляется тост, завершается фоновое сохранение, фильтр меняет количество результатов. У пользователя скринридера нет способа узнать об этом, если вы не объявите изменение через **живую область** (live region).

Компонент `Notifications` в Altrone уже настроен для этого. Если вы строите собственный UI для асинхронной обратной связи вне него, применяется тот же паттерн:

```tsx
function SaveStatus({ status }: { status: 'idle' | 'saving' | 'saved' }) {
  return (
    <div aria-live="polite" role="status">
      {status === 'saving' && 'Сохранение…'}
      {status === 'saved' && 'Сохранено'}
    </div>
  );
}
```

Используйте `aria-live="polite"` для рутинных обновлений статуса (сохранение завершилось, изменился счётчик) — он ждёт, пока скринридер закончит озвучивать текущий текст. `aria-live="assertive"` оставьте для того, что действительно требует немедленного прерывания — например, истечение сессии; применение его к рутинным обновлениям мешает больше, чем помогает.

## Контраст и недопустимость цвета как единственного сигнала

Текст и значимые элементы интерфейса должны соответствовать **WCAG AA**: контраст 4,5:1 для обычного текста, 3:1 для крупного текста (≥18pt / 24px, либо ≥14pt полужирным) и для границ элементов интерфейса (рамка поля ввода, рамка фокуса).

Всегда собирайте цветовые сочетания из семантических токенов-ролей Altrone (`--danger-text-1`, `--success-solid-1`, `--text-*`, …, см. раздел [Цвет](color)), а не подбирайте произвольный hex-код — токены уже выверены под AA, а самостоятельно подобранный цвет может и не пройти проверку.

Вторая половина этого правила не менее важна: **состояние никогда не должно передаваться только цветом.** Красная рамка поля без другого сигнала невидима для пользователя с нарушением цветовосприятия (и для любого, кто смотрит бегло). Сопровождайте цвет иконкой, текстом или и тем, и другим.

:::col-2
**Только цвет — не проходит**

```tsx
<TextInput
  label="Email"
  style={{ borderColor: 'var(--danger-border-1)' }}
/>
```

---

**Цвет + текст + иконка — проходит**

```tsx
<Form.Field
  label="Email"
  name="email"
  errorMessage="Введите корректный email"
>
  <TextInput />
</Form.Field>
```
:::

## Сниженная анимация: убирать декоративное, оставлять обратную связь

Учитывайте `prefers-reduced-motion`, но не применяйте его слишком широко. Смысл требования WCAG (2.3.3) уже, чем «выключить всю анимацию целиком»: оно касается движения, которое **декоративно, автоматически проигрывается или зациклено без информационной нагрузки.** Движение как прямая обратная связь на только что совершённое пользователем действие — не об этом, и его удаление может сделать интерфейс менее отзывчивым, а не более доступным.

Два реальных примера из компонентов самой Altrone, которые осознанно решены по-разному:

- Мерцание скелетона (shimmer) чисто декоративно — оно не сообщает ничего такого, чего не сообщал бы статичный серый блок. Полностью отключается при сниженной анимации.
- Спиннер загрузки — функциональный индикатор состояния, единственный сигнал о том, что фоновая операция всё ещё выполняется. Он продолжает вращаться при сниженной анимации, потому что его удаление убрало бы единственную обратную связь о том, что что-то происходит.

Если вы добавляете ручную JS-синхронизацию по времени (не CSS-переход, который `prefers-reduced-motion` обрабатывает сам через обычные медиазапросы), используйте тот же SSR-безопасный хук, что и остальная Altrone, вместо того чтобы зашивать длительность в код:

```tsx
import { useMediaMatch } from 'altrone-ui';

function useAutoDismiss(onDismiss: () => void) {
  const reducedMotion = useMediaMatch('(prefers-reduced-motion: reduce)');
  const delay = reducedMotion ? 0 : 300;

  useEffect(() => {
    const timer = setTimeout(onDismiss, delay);
    return () => clearTimeout(timer);
  }, [onDismiss, delay]);
}
```

:::note
Если не уверены, должна ли конкретная анимация останавливаться при сниженной анимации или продолжать работать — не гадайте: два примера выше пришли к противоположным ответам по конкретной причине, связанной с тем, что именно это движение сообщало. Лучше спросить, чем по умолчанию отключать всё подряд.
:::

## Зона нажатия: не менее ~24px даже в самом маленьком размере

Видимый размер контрола и его реальная область нажатия/тапа — разные вещи. Даже при самом маленьком размере Altrone, `size="mini"`, фактическая зона нажатия остаётся не менее ~24px — как правило, за счёт невидимого padding, выходящего за пределы отрисованной границы — чтобы контролом можно было пользоваться и при ограниченной мелкой моторике, и в целом на сенсорных устройствах.

Если вы проектируете собственный компактный контрол, не давайте «маленькому» схлопнуть зону нажатия вместе с визуальным размером:

```scss
/* Видимая 16px-иконка всё равно нуждается в реальной зоне нажатия */
.miniIconButton {
  width: 16px;
  height: 16px;
  padding: 4px; /* увеличивает эффективную зону нажатия до 24px */
}
```

## Валидация формы: `aria-invalid` + `aria-describedby`

Красная рамка сообщает о невалидном состоянии визуально, но пользователю скринридера нужно ещё две вещи, настроенные явно: поле должно быть помечено как невалидное (`aria-invalid="true"`), а сообщение об ошибке должно быть программно связано с полем (`aria-describedby`), чтобы оно озвучивалось при фокусировке или осмотре этого поля — а не просто находилось рядом в DOM без какой-либо связи.

`Form.Field` в Altrone автоматически выставляет `aria-invalid` на дочернем поле ввода, как только вы передаёте ему `errorMessage` — но пока не связывает сообщение с полем через `aria-describedby`, так что если вы собираете полностью кастомное поле из сырых элементов, эту часть нужно настроить самостоятельно:

```tsx
function CustomField({ error }: { error?: string }) {
  const id = useId();
  const errorId = `${id}-error`;

  return (
    <div>
      <label htmlFor={id}>Промокод</label>
      <input
        id={id}
        aria-invalid={Boolean(error)}
        aria-describedby={error ? errorId : undefined}
      />
      {error && (
        <span id={errorId} role="alert">
          {error}
        </span>
      )}
    </div>
  );
}
```

## Чек-лист для собственных компонентов

Когда вы расширяете Altrone своим компонентом, перед тем как считать его готовым, пройдитесь по этому списку:

:::col-2
**Частые упущения**

- Контрол только с иконкой без `aria-label`
- Кастомный оверлей, не возвращающий фокус при закрытии
- `:focus` вместо `:focus-visible`
- Изменение статуса, не объявленное через `aria-live`
- Невалидное поле с красной рамкой и ничем больше

---

**Что проверить вместо этого**

- У каждого контрола только с иконкой есть доступное имя
- Закрытие любого оверлея восстанавливает фокус на его триггере
- Рамка фокуса появляется только при навигации с клавиатуры / вспомогательных технологий
- Асинхронные изменения статуса обёрнуты в живую область
- Невалидное состояние сопровождает цвет текстом/иконкой, плюс `aria-invalid` + `aria-describedby`
:::

:::tip
Начинайте с нативных HTML-элементов и семантики всегда, когда это позволяет компонент — `<button>`, `<label htmlFor>`, нативный `<dialog>`. Вы получаете поддержку клавиатуры, роли и поведение фокуса бесплатно, и ARIA нужно добавлять только там, где нативный HTML действительно не справляется.
:::
