# Макеты и адаптивность

Лэйаут в Altrone — это две связанные, но разные задачи: как вы *компонуете* экран (`Flex`, `Grid`, `Box`, `Screen`) и как эта композиция *адаптируется* при изменении вьюпорта или размера самого контейнера. Эта статья покрывает обе — примитивы, из которых вы строите, и модель, которую Altrone использует, чтобы делать их отзывчивыми без того, чтобы каждый компонент изобретал свою собственную логику брейкпоинтов.

## Композиция лэйаута

**`Flex`** — одномерная рабочая лошадка: строка или колонка с отступом, выравниванием и переносом:

```tsx
<Flex orientation="vertical" gap="m" align="start">
  <Text size={9} weight="bold">Заголовок</Text>
  <Text color="muted">Вводный абзац</Text>
</Flex>
```

**`Grid`** — двумерный аналог: 12-колоночная сетка, где каждый `Grid.Column` занимает пролёт (`1`–`12`, либо `'auto'`) и опциональный отступ:

```tsx
<Grid gap="m" rowGap="m">
  <Grid.Column size={8}>
    <Text>Основной контент</Text>
  </Grid.Column>
  <Grid.Column size={4}>
    <Text>Боковая панель</Text>
  </Grid.Column>
</Grid>
```

`size` у `Grid.Column` — это одно явное значение, он не принимает адаптивный объект (`{ xs: 12, md: 6 }`). Если пролёт колонки должен меняться на определённом брейкпоинте, вы решаете это явно в своём коде (см. [Брейкпоинты вьюпорта](#брейкпоинты-вьюпорта) ниже), а не полагаетесь на то, что сетка выведет это сама.

**`Box`** — универсальный примитив-поверхность, лежащий в основе многих компонентов библиотеки (форма, материал, тон, elevation) — обращайтесь к нему, когда нужен стилизованный контейнер, не подходящий ни под один из перечисленных выше.

**`Splitter`** покрывает изменяемый пользователем, перетаскиваемый лэйаут — два или более `Splitter.Panel` с перетаскиваемым разделителем между ними, каждая панель опционально сворачиваемая. Используйте его, когда границу должен регулировать сам пользователь (боковую панель можно растянуть или скрыть), а не просто адаптировать её под размер вьюпорта.

**`Screen`** — лэйаут оболочки приложения: `Screen.Header`, `Screen.Sidebar`, `Screen.Content`, `Screen.Aside`, `Screen.Footer`, `Screen.BottomNavigation` как именованные зоны в одной сетке, вместо того чтобы позиционировать каждую вручную. Именно здесь и живёт большая часть адаптивного поведения ниже.

## Двухуровневая модель адаптивности

Altrone разделяет «адаптивность» на два самостоятельных механизма, каждый под свой тип решения:

- **Брейкпоинты вьюпорта** (`useBreakpoint()`) — для решений *уровня приложения*: должна ли боковая панель быть постоянной колонкой или оверлеем, должна ли вообще показываться мобильная навигация.
- **Контейнерные запросы** (`useContainerQuery()` / `useElementSize()`) — для решений *уровня компонента*: есть ли у конкретного блока (который может сидеть внутри панели `Splitter`, карточки, узкой колонки) место для расположения элементов рядом, независимо от вьюпорта.

Обращайтесь к брейкпоинтам вьюпорта, когда ответ действительно зависит от всего экрана. Обращайтесь к контейнерным запросам, когда он зависит от того пространства, которое реально есть у конкретного элемента — `Screen`, встроенный в узкую панель `Splitter`, должен адаптироваться под ширину *этой панели*, а не окна браузера.

### Брейкпоинты вьюпорта

```tsx
import { useBreakpoint } from "altrone-ui";

function Example() {
  const { isMd } = useBreakpoint();
  return isMd ? <SidebarNav /> : <BottomTabBar />;
}
```

| Имя | Мин. ширина |
| --- | --- |
| `xs` | 520px |
| `sm` | 768px |
| `md` | 1024px |
| `lg` | 1280px |
| `xl` | 1640px |

Каждый `is{Name}` — это `min-width`, «вьюпорт не уже этого значения», а не взаимоисключающий диапазон. Хук SSR-safe: все флаги равны `false`, пока компонент не смонтировался и не смог реально измерить вьюпорт — так что серверный рендер никогда не должен гадать, а потом самоисправляться вспышкой.

### Контейнерные запросы

Для чисто визуальных изменений — скрыть элемент, изменить количество колонок сетки — предпочитайте обычный CSS `@container` вместо JS целиком; он свободен от проблем рассинхронизации с SSR, описанных ниже, и вообще не требует хука. Обращайтесь к `useContainerQuery`/`useElementSize` только когда решение должно приниматься в JS/React — структурное изменение вроде замены того, какой компонент рендерится, а не просто того, как он стилизован:

```tsx
import { useRef } from "react";
import { useContainerQuery } from "altrone-ui";

function ListDetail() {
  const ref = useRef<HTMLDivElement>(null);
  const isNarrow = useContainerQuery(ref, { maxWidth: 480 });

  return (
    <div ref={ref}>
      {isNarrow ? <StackedLayout /> : <SideBySideLayout />}
    </div>
  );
}
```

Как и `useBreakpoint`, это SSR-safe: возвращает `false`, пока элемент реально не измерен после монтирования, вместо того чтобы гадать о размере, который сервер знать не может.

## Визуальная адаптивность vs структурная

Не каждое адаптивное изменение требует одного и того же инструмента:

- **Визуальная адаптивность** — скрыть элемент, изменить число колонок сетки, поправить отступы — это чистый CSS (`@container`, медиа-запросы). Без JS, без риска рассинхронизации с SSR.
- **Структурная адаптивность** — реальная замена того, какой лэйаут рендерится, например схлопывание List-Detail из двух панелей в одну — требует JS, потому что два лэйаута — это разные деревья компонентов, а не просто разное оформление одного и того же. Именно для этого нужны `useContainerQuery`/`useElementSize` и `useBreakpoint`.

## Адаптивность — это смена навигационной идиомы, а не просто изменение размера

Самый наглядный пример структурной адаптивности в Altrone — то, как `Screen` полностью меняет навигационную идиому, а не просто сжимает боковую панель, заменяя её другим паттерном:

```tsx
<Screen mobileBreakpoint="md">
  <Screen.Sidebar visibleFrom="md">
    <SidebarNav />
  </Screen.Sidebar>

  <Screen.Content>{children}</Screen.Content>

  <Screen.BottomNavigation hiddenFrom="md">
    <BottomTabBar />
  </Screen.BottomNavigation>
</Screen>
```

`visibleFrom="md"` и `hiddenFrom="md"` означают ровно то, что написано — ниже `md` боковой панели вообще нет в DOM (а не просто скрытой, но занимающей место в лэйауте); на `md` и выше нет нижней панели. Ниже собственного `mobileBreakpoint` компонента `Screen`, `Screen.Sidebar` дополнительно переключается из встроенной колонки сетки в закадровый оверлей со скримом — это отдельная ось от того, рендерится ли зона вообще.

:::tip
Не задавайте ни `visibleFrom`, ни `hiddenFrom`, чтобы зона оставалась смонтированной всегда — её *режим* всё равно может адаптироваться (боковая панель уходит в оверлей ниже `mobileBreakpoint`), даже когда её *присутствие* не меняется.
:::

## `size` остаётся явным

Проп `size` компонента (`mini`/`s`/`m`/`l`/`xl`) — это всегда то, что задаёт автор, он никогда не меняется неявно в зависимости от текущего брейкпоинта. Если контрол должен быть меньше на мобильном — это решение, которое вы принимаете явно (через `useBreakpoint` или контейнерный запрос), а не поведение, которое `size` подсовывает вам сам. Это соответствует общему предпочтению проекта в пользу явной конфигурации вместо скрытой магии, управляемой брейкпоинтами.

## Построение собственных компонентов

1. **Компонуйте через `Flex`/`Grid`/`Box`, а не через сырой `display: flex`/`grid` в самописном CSS.** Единые примитивы означают единые токены отступов/выравнивания и предсказуемое поведение везде, где они используются.
2. **Выбирайте инструмент адаптивности под конкретное решение, а не по умолчанию.** Чисто визуальное изменение сначала тянется к CSS `@container`; структурное — к `useContainerQuery`; решение уровня приложения — к `useBreakpoint`. Не используйте `useBreakpoint` по умолчанию для того, что на самом деле должно быть привязано к контейнеру.
3. **Никогда не давайте `size` меняться самому в зависимости от вьюпорта или контейнера.** Если для вашего компонента правильно быть меньше на мобильном — пусть вызывающий код (или ваша собственная проверка через `useBreakpoint`) явно передаёт другой `size` — не позволяйте компоненту молча переопределять то, что было задано.
4. **Структурная, управляемая JS адаптивность требует SSR-safe паттерна.** И `useBreakpoint`, и `useContainerQuery` возвращают значение по умолчанию «пока не известно» (`false`) до монтирования — специально для того, чтобы серверная разметка и первый клиентский рендер совпадали. Компонент, измеряющий собственный размер, должен следовать той же форме, а не читать `window`/лэйаут синхронно во время рендера.
