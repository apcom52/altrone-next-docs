# Ввод данных

В Altrone много отдельных компонентов ввода — `TextInput`, `NumberInput`, `PasswordInput`, `AutocompleteInput`, `Search`, `TextArea`, `Select`, `Checkbox`, `Radio`, `Switch`, `Slider`, `ColorPicker`, `DatePicker`, `FilePicker` — но это не четырнадцать независимых конструкций. Большинство из них разделяют одну сигнатуру события, а некоторые — ещё и одно визуальное шасси, даже собирая совсем разные по форме значения. Эта статья — про этот общий фундамент, сгруппированный по тому, какое значение на самом деле производит каждый контрол.

## Одна сигнатура события везде

Любой колбэк вроде `onChange` принимает сначала смысловое значение, а нативное DOM-событие — последним аргументом, никогда не наоборот и никогда только событие:

```ts
// TextInput
onChange?: (value: string, event: ChangeEvent) => void;
// Checkbox
onChange?: (state: boolean, event: ChangeEvent<HTMLInputElement>) => void;
// Radio
onChange: (value: string, event: ChangeEvent<HTMLInputElement>) => void;
```

Практический эффект: вам почти никогда не нужен `event.target.value` — нужное значение уже приходит первым аргументом, типизированным правильно для конкретного контрола.

## Свободный текст: `TextInput` и построенные на нём контролы

`NumberInput`, `PasswordInput`, `AutocompleteInput`, `Search` и `TextArea` не строят собственное оформление поля с нуля — внутри каждый рендерит `TextInput` и надстраивает своё поведение поверх него:

```tsx
const [value, setValue] = useState("");

<TextInput value={value} onChange={setValue} placeholder="Ваше имя" />;
```

Сам `TextInput` — это `Box` со слотовой системой под названием **островки** (islands) — небольшие блоки, которые пристыковываются к краю `start` или `end` поля как дочерние элементы:

| Островок | Назначение |
| --- | --- |
| `TextInput.TextIsland` | Статический текст — символ валюты, префикс URL, единица измерения |
| `TextInput.IconIsland` | Неинтерактивная иконка, сигнализирующая о назначении поля |
| `TextInput.ActionIsland` | Полноценная `Button`, пристыкованная к полю (кнопка очистки, переключатель видимости пароля) |
| `TextInput.LoadingIsland` | Индикатор загрузки внутри поля |
| `TextInput.CustomIsland` | Что угодно ещё, что нужно пристыковать к краю |
| `TextInput.CharCounterIsland` | Живой счётчик символов |

```tsx
import { Search, X } from "lucide-react";

<TextInput value={search} onChange={setSearch} placeholder="Поиск">
  <TextInput.IconIsland icon={<Search size={16} />} placement="start" />
  {search && (
    <TextInput.ActionIsland
      label="Очистить"
      icon={<X size={16} />}
      showLabel={false}
      placement="end"
      onClick={() => setSearch("")}
    />
  )}
</TextInput>
```

Переключатель видимости пароля у `PasswordInput` и кнопка очистки у `Search` — это оба просто `ActionIsland`, тот же самый механизм, к которому вы обратились бы в собственной композиции, а не особый случай.

## Структурированные значения, которые всё равно выглядят как текстовое поле: `ColorPicker` и `DatePicker`

Цвет и дата — не строки, но их выбор всё равно выигрывает от той же формы «кликнуть по полю, увидеть отформатированное значение, открыть что-то, чтобы его поменять» — поэтому и `ColorPicker`, и `DatePicker` по умолчанию рендерят внутри `TextInput` в качестве триггера, тот же компонент, на котором построены `NumberInput`/`Search`:

```tsx
// ColorPicker: значение — строка цвета; поповер — выбор из палитры/пресетов
<ColorPicker value={color} onChange={setColor} colorPresets={presets} />

// DatePicker: значение — объект Dayjs; поповер — календарь
<DatePicker value={date} onChange={setDate} format="DD.MM.YYYY" />
```

Оба принимают `asChild`, чтобы полностью заменить триггер по умолчанию (`TextInput`) на что-то другое — кнопку, кастомный чип — сохранив при этом то же поведение поповера.

## Булевы и одиночный выбор: `Checkbox`, `Switch`, `Radio`

Эти контролы собирают более простую форму значения, чем свободный текст — булево (`Checkbox`, `Switch`) или одну строку/число из фиксированного набора (`Radio`) — и являются самостоятельными контролами, а не построенными на `TextInput`:

```tsx
<Checkbox checked={agreed} onChange={setAgreed}>Я согласен</Checkbox>
<Switch checked={enabled} onChange={setEnabled}>Включено</Switch>
```

## Непрерывные значения: `Slider`

Значение `Slider` — обычное число, но он предоставляет **два** колбэка изменения, а не один:

```ts
onChange: (value: number, event) => void; // срабатывает непрерывно во время перетаскивания
onChangeEnd?: (value: number, event) => void; // срабатывает один раз, когда перетаскивание завершается
```

Обращайтесь к `onChangeEnd` для всего затратного — сетевого запроса, тяжёлого пересчёта — чтобы он выполнялся один раз за взаимодействие, а не один раз за каждый пиксель перетаскивания. `onChange` остаётся для дешёвых, чисто визуальных обновлений (вроде живой подписи с текущим значением).

## Коллекции файлов: `FilePicker`

Значение `FilePicker` всегда — **список** `FileItem` — `value`/`defaultValue` это `FileItem[]`, никогда одиночный `File`, даже когда `multiple` выключен. Это значит, что вызывающему коду никогда не нужно отдельно обрабатывать случаи «один файл» и «много файлов»:

```tsx
<FilePicker
  value={files}
  onChange={setFiles}
  multiple
  accept="image/*"
/>
```

Он также может сам заниматься загрузкой — передайте `url`/`method` (и опционально `autoUpload`), и он сам выполнит запрос, сообщая о прогрессе через `autoUploadFn`; либо пропустите всё это и просто читайте список файлов из `onChange`, чтобы загрузить их как вам нужно.

## Построение собственных компонентов

1. **Следуйте сигнатуре `(value, event)`** для любого колбэка в форме `onChange` — сначала значение, нативное событие последним, никогда не только событие.
2. **Если ваш контрол текстовый, стройте его на `TextInput`** (компонуйте, а не оборачивайте сырой `<input>`), чтобы бесплатно унаследовать систему островков и оформление `Box`.
3. **Если вашему контролу нужен паттерн «кликнуть по полю, открыть что-то для выбора значения»** (как это устроено у `ColorPicker`/`DatePicker`), рассмотрите возможность построить его триггер тоже на `TextInput`, с `asChild` как запасным путём для полностью кастомного триггера.
4. **Непрерывное перетаскивание** — разделяйте живой `onChange` и финальный `onChangeEnd`, как это делает `Slider`, вместо того чтобы выполнять затратную работу на каждом кадре перетаскивания.
5. **Моделируйте значение, собирающее файлы, как список, даже когда разрешён только один файл** — это избавляет вызывающий код от отдельной обработки количества.
